## 2026-08-11 ~22:57 CDT — revoke Phase 1: the kill switch is retroactive

**WHAT.** Evan's decision of the same day: a guardian's revoke must pull the minor

**The design decision, and why.** The org must still SEE the student afterwards
(greyed, per Evan), so deleting the Application — which is what a student's own

What does the work is one field. Every consumer of roster membership keys on

waitlist for approved one-time events, reusing the exact rule from
`withdraw_application` rather than inventing a second one. The count of withdrawn
applications goes into the `consent_revoked` audit row, so the unwind is auditable
rather than inferable from missing rows.

any recipient where `consent_blocks` is true, checked LIVE rather than by
filtering on application status — so it also covers a minor gated for any other
reason, and un-gates automatically if consent is restored. That matters because
`create_notification` sends email: a delivered broadcast is a real email to a
child whose guardian just withdrew permission.

## 2026-08-12 ~21:45 CDT — the rate limiter stopped keying on the proxy

**WHAT.** Finding 8 from the 2026-08-12 cold audit, the last substantive item
open from it. Behind a reverse proxy `request.client.host` is the PROXY, so every
user shared one bucket: the auth cap was effectively 30/min GLOBALLY, one abusive
client could lock out the entire user base, and the per-client limit did nothing.

**The obvious fix is worse than the bug, and that shaped the design.**
`X-Forwarded-For` is attacker-supplied. Reading it unconditionally lets any client
vary the header per request, mint a fresh bucket each time, and bypass the limiter
completely — trading a shared-bucket DoS for no limiter at all. So the header is
ignored unless the deploy states its topology.

`TRUSTED_PROXY_HOPS` (default **0** — trust nothing) is that statement. Each proxy
APPENDS the address it received from, so with N trusted hops the real client is
the Nth entry from the right. `client_ip()` returns the socket address whenever
that cannot be justified: hops unset, header absent, chain SHORTER than declared
(the request did not traverse the path we were told about), or an entry that is
not a parseable IP.

**Five tests, written first and all red before the change.** The most important is
`test_forwarded_header_is_IGNORED_by_default`, which sends a different spoofed
client per request and asserts the limiter still fires — that is the property a
careless implementation would destroy. Then: two real clients behind one declared
proxy get separate budgets (and a control asserting client B is NOT punished for
client A's burst — the actual user-facing symptom); a 2-hop chain keys on the
client rather than the rotating CDN node; malformed headers (`not-an-ip`, empty,
whitespace, a SQL-injection string) all fall back to one bucket instead of minting
four; and a chain shorter than declared does not IndexError or get trusted.

**Documented in all three places an operator actually looks**, because the failure
is silent — nothing errors, the limiter just stops working. `backend/.env.example`,
`DEPLOY.md` §post-deploy, and `DEPLOY_RAILWAY.md`'s env list, which now says
plainly that Railway terminates TLS at its own proxy so without this the whole
user base shares one bucket and the limiter is decorative. `DEPLOY.md` also loses
the line under "Known production hardening still owed" that asked for exactly
this — leaving a completed item on a TODO list is how the next reader re-does it.
`security.md` corrected: it had said "trust validated `X-Forwarded-For` at M11".

**NOT fixed, and still true:** the limiter remains in-memory and single-process, so
a multi-replica deploy still multiplies every limit by the replica count. That is
the Redis half of finding 8 and it is untouched — this change fixes WHO gets
counted, not WHERE the count lives.
